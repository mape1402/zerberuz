# Zerberuz v0.8 - Global Configuration And Locked Cache Plan

## Decision

Zerberuz should support one global configuration file per machine/team image and should not let individual projects choose the cache path.

The analyzer and CLI can still read a project-level `zerberuz.json` when a repository needs to pin a profile/version, but the preferred flow is global:

```text
global config -> team/profile/server/version
Zerberuz-owned cache path -> rules-cache.json/help/latest-compatible pointer
project build -> analyzer reads local cache
```

## Why

The cache contains downloaded rule definitions used by analyzers. If every project can choose `cacheRoot`, a developer can point the analyzer at modified local definitions and bypass governance. The cache location should be a Zerberuz-owned implementation detail, not a project setting.

## Pros Of Global Configuration

- One onboarding step per machine/team image.
- Consistent `team`, `profile`, `rulesEndpoint`, and default `rulesVersion`.
- Less repo noise because not every project needs `zerberuz.json`.
- Easier CI/container images: bake config once, reuse everywhere.
- Cleaner governance: projects consume policy instead of redefining how policy is found.

## Cons Of Global Configuration

- Less explicit per repository; a project may behave differently across machines if global config drifts.
- Multi-team machines need a clear override story for `profile` or `team`.
- IDE diagnostics depend on local machine provisioning.
- Debugging needs `doctor` to show exactly which config file was resolved.

## Cache Policy

Remove public cache path selection:

- No `cacheRoot` in config.
- No `--cache-root` CLI option.
- No `ZERBERUZ_CACHE_ROOT` environment override.

Use Zerberuz-controlled defaults:

```text
Windows: %PROGRAMDATA%/Zerberuz/cache
Linux/macOS with common app data: <common-app-data>/Zerberuz/cache
Fallback: ~/.zerberuz/cache
```

Tests may inject a cache root through internal/test-only delegates, but users should not see or configure it.

## Global Configuration Path

Default global configuration path:

```text
Windows: %PROGRAMDATA%/Zerberuz/zerberuz.json
Linux/macOS with common app data: <common-app-data>/Zerberuz/zerberuz.json
Fallback: ~/.zerberuz/zerberuz.json
```

Example:

```json
{
  "team": "elysium",
  "profile": "backend",
  "rulesVersion": "latest-compatible",
  "mode": "latest-compatible",
  "rulesEndpoint": "https://zerberuz.company.test"
}
```

## Resolution Rules

Analyzer:

1. Additional file named `zerberuz.json`, when present.
2. Global config file.
3. Built-in defaults.

CLI:

1. `--config-path`, when present.
2. Local `zerberuz.json`, when present.
3. Global config file.
4. Built-in defaults for `init`.

## Acceptance

- Analyzer no longer reads `cacheRoot`.
- CLI no longer accepts `--cache-root`.
- Docs explain global config and locked cache.
- Existing tests remain deterministic through injected path resolvers.
- `dotnet build Zerberuz.slnx -c Release` passes.
- `dotnet test Zerberuz.slnx -c Release --no-build` passes.
